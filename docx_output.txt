Rabyte-Tech
Digital Product Discovery Marketplace
Full Architecture + URL Product Importer + Profile-as-Store
Version 2.0 • October 2026
Core product rule: Rabyte-Tech is a free digital-product discovery and listing marketplace. It does not process the underlying sale. A visitor discovers a product on Rabyte-Tech and is sent to the seller's original external product page or checkout URL.
Major architecture update: the seller's normal user profile acts as the seller's public storefront. There is no separate Store entity, no separate Store Name field, and no Store Category field. Sellers add products to their profile, and visitors can browse all of that seller's published products from the profile page.
Major onboarding update: sellers can paste a valid product-page URL. The platform detects the supported source, fetches the public page server-side, extracts available product metadata/content, creates a draft, and lets the seller review and edit it before publishing. No third-party product API is required for the initial implementation.

1. Product Goal
Build a clean, premium, SEO-friendly directory where creators can list digital products such as eBooks, software, templates, courses, AI tools, design assets and other digital goods. Rabyte-Tech provides discovery, product presentation, profile-level seller exposure, reviews and outbound traffic measurement. The actual transaction remains on the seller's external platform.
Primary user journey: Discover → Open product → Review → Click external purchase link.
Seller journey: Register → Paste product URL → Import → Review/edit → Add primary image → Submit → Publish.
Seller profile journey: Open seller profile → See seller credibility and product catalogue → Open any product.
No native payment gateway, wallet, checkout or digital-file delivery in MVP.
2. Core Product Principles
Keep seller onboarding extremely low-friction.
Never require the seller to manually retype information that is publicly available on the source product page when it can be safely extracted.
Treat imported information as a draft, not as unquestioned truth.
Keep source URL and source platform metadata for traceability.
Do not claim external sales, revenue or conversion numbers as Rabyte-Tech-verified facts.
The seller controls their profile and can manage their listed products from one dashboard.
A product must resolve to a specific product/detail page. A generic store homepage or domain root is not an acceptable product URL.
Rabyte-Tech should host its own primary product cover image instead of depending on external image hotlinking.
3. Seller Profile as Storefront
The seller profile is the storefront. There is no separate Store object in the product model. A public user profile can function as a catalogue page containing the seller's identity, credibility information and published products.
3.1 Public seller profile URL
Recommended route: /seller/[username] or /u/[username]. The final route should be chosen once during implementation and used consistently for canonical URLs.
3.2 Profile page layout
Profile avatar/logo.
Seller display name.
Short seller bio/about text.
Joined date or member-since information, if desired.
Total published products.
Average product rating.
Total ratings/reviews.
Total approved testimonials.
Top testimonials section.
Published product grid.
Product categories represented by the seller, derived from listed products rather than stored as a Store Category.
Optional external social/profile links.
Report profile action.
The page should visually feel like a storefront, but the data model remains a user profile. This avoids creating a second identity layer and keeps account management simple.
3.3 What is deliberately NOT present
No separate Store Name.
No separate Store ID.
No separate Store Category.
No store subscription.
No store-level checkout.
No store-level payment processing.
4. Product URL Importer
The importer is the primary seller onboarding mechanism. The seller pastes a direct product-page URL. The backend detects the source platform, fetches the public page, extracts available information and creates an editable product draft.
4.1 Seller flow
Seller opens Dashboard → Add Product.
Seller pastes a direct product-page URL.
Client performs basic syntax validation.
Server performs strict URL validation and platform detection.
Server fetches the public page with controlled timeouts and response-size limits.
Platform adapter attempts structured extraction first.
Generic metadata extraction is used as fallback.
Extracted fields are normalized into the Rabyte-Tech product draft model.
Seller reviews the imported data.
Seller may edit the title, description, category, tags and other marketplace fields.
Seller uploads one primary cover image for Rabyte-Tech.
Seller confirms the listing.
System checks duplicate URL/product conditions and moderation rules.
Product enters pending or published state according to the configured moderation mode.

5. Strict Product URL Rules
The URL rule is intentionally strict. A seller cannot submit only a domain root or generic store homepage and call it a product. The marketplace needs a specific product page so the listing represents one identifiable product.

Validation must not rely only on URL shape. After fetching, the server must confirm that the page contains product-level evidence such as a product title, canonical/product metadata, purchase CTA, structured product information or other platform-specific indicators.
5.1 Redirect handling
Redirects are allowed only when the final destination remains within an approved/validated source or clearly resolves to the intended product page. Redirect chains must be limited and private/internal destinations must be blocked.
5.2 Duplicate protection
Normalize the canonical URL before duplicate comparison.
Prevent the same external product URL from being submitted repeatedly by the same or different sellers unless an admin override is used.
Keep the original submitted URL and final canonical URL for auditability.

7. Source-Reported Sales Data
The requested sales-count feature is supported as an opportunistic extraction. If a source page publicly exposes a sales number, the importer can store it as source-reported data.
Database field example: source_sales_count.
Additional field: source_sales_count_visible = true/false.
Additional field: source_sales_count_checked_at.
Public UI label should be 'Sales reported by source' or similar, not 'Verified sales'.
If the page does not expose a sales count, do not invent one and do not infer sales from likes, reviews or traffic.
Rabyte-Tech should never combine source-reported sales with Rabyte-Tech click analytics and call the result revenue or verified sales.
8. Image Strategy
The revised MVP deliberately avoids depending on external product images. External image URLs can disappear, change, block hotlinking or change permissions. Rabyte-Tech therefore keeps its own primary marketplace image.
8.1 MVP image rule
One primary product cover image is the standard seller upload.
Seller can replace the image before or after publication.
Optional additional images can be supported later without changing the core model.
Imported source image URLs may be recorded as temporary extraction metadata, but the published marketplace page should use the R2-hosted marketplace image.
Use Cloudflare R2 for the actual stored image.
D1 stores the R2 key and image metadata, not the binary file.
8.2 Upload flow
Seller selects/upload the primary image.
Server validates MIME type, file size and dimensions.
Browser uploads directly to R2 using a short-lived presigned upload URL.
Worker verifies/records the object metadata.
D1 stores the R2 object key, alt text and sort order.

10. Seller Profile / Storefront UI
Recommended visual structure:
Header: avatar, seller name, short bio, joined date.
Trust strip: average rating, total reviews, published product count.
Top testimonials: 2–4 strongest approved testimonials.
Product catalogue: responsive product grid.
Category chips: derived dynamically from the seller's listed products, not a manually selected Store Category.
Product sorting: newest, top rated, most viewed, most clicked.
Profile report action.
The seller page should look and behave like a store because visitors need a catalogue experience, but the system should continue to describe it internally as a public seller profile. This keeps the identity model simple and avoids duplicated seller/store records.
11. Reviews, Ratings and Testimonials
Rabyte-Tech's own rating system is separate from any rating that may be visible on an external source page.
Rabyte-Tech rating: generated from reviews submitted on Rabyte-Tech.
Source rating: imported only when publicly visible and clearly labelled as source data.
Rabyte-Tech testimonials: approved reviews/testimonials from Rabyte-Tech users.
Top testimonials on seller profile: rank approved testimonials using rating, recency and moderation status.
Do not silently merge external reviews with internal reviews.
12. Category Model
Products still have categories. Sellers do not create a separate Store Category. When importing a product, the system should first attempt to map the source category into a Rabyte-Tech category. The seller can correct the product category before submission.
Example marketplace categories: eBooks, Software, Templates, Courses, AI Tools, Design Assets, Marketing, Business, Productivity, Creator Tools.
Seller profile categories are derived from the seller's published products.
Future country-specific ranking must operate independently from the category model.
13. Future Country-Aware Ranking
The requested country-aware logic is intentionally deferred. The architecture should nevertheless store the signals needed to add it later.
Store anonymous/consented coarse location or country-level request signal where legally and technically appropriate.
Maintain a product source/country relevance score separately from the core product record.
Future example: visitors from India may receive higher ranking exposure for selected CosmoFit products.
Do not hard-code the India/CosmoFit rule into the initial product ranking implementation.
Future ranking can combine country, category, freshness, rating, engagement and paid featured placement.

25. Cloudflare Architecture
Recommended full-stack deployment remains Cloudflare Workers with Next.js/vinext. Use D1 for relational data, R2 for images, KV only where eventual consistency is acceptable, Email Service for transactional mail, Email Routing for inbound mail and Turnstile/WAF/rate limiting for abuse controls.
High-level flow:
Browser → Cloudflare DNS/CDN → Next.js on Workers → D1 + R2 + KV (selectively) + Email Service + Turnstile/WAF
Importer flow:
Seller URL → Worker validation → Platform adapter → public page fetch → extraction/normalization → draft in D1 → seller review → publish
Purchase flow:
Rabyte-Tech product page → outbound event → external product page/checkout → user may return
26. Security Baseline
Never store plaintext passwords.
Never expose Cloudflare credentials or secrets to the browser.
Use strict SSRF protections for the URL importer.
Block localhost, RFC1918/private ranges and internal destinations.
Limit fetch timeout, response bytes and redirect count.
Sanitize imported HTML before rendering.
Use a safe allowlist for external protocols; HTTPS only for product URLs.
Use R2 presigned uploads with short expiry.
Rate-limit authentication, importer, review and contact endpoints.
Use Turnstile where appropriate.
Require admin role checks on every admin mutation endpoint.
Record audit events for imports, bans, edits, featured placements and admin actions.
27. Copyright, Content Rights and Source Compliance
The importer must not be treated as permission to copy anything that is not lawfully available for reuse. The initial implementation should prefer public metadata and product information needed to create a listing, while avoiding unnecessary duplication of protected content. The seller should confirm that they have the right to list and promote the product and the associated information.
Provide a DMCA/copyright reporting route.
Allow admins to remove listings and source-derived content when a valid complaint is received.
Do not import private/authenticated content.
Do not bypass paywalls, login walls, CAPTCHAs or access controls.
Do not claim that imported third-party sales numbers or ratings are independently verified.
Keep a source URL and import timestamp for auditability.

32. Final Architecture
User account = identity + seller profile + product catalogue. There is no separate Store entity.
Product listing = Rabyte-Tech presentation layer + external source URL. Rabyte-Tech does not own or process the underlying transaction.
Importer = URL-only, server-side public-page extraction with platform adapters. No third-party product API is required for the initial release.
Images = seller-uploaded primary cover stored in R2. Do not rely on permanent external image hotlinks.
Analytics = Rabyte-Tech page views, unique/return visitors, outbound clicks, ratings and testimonials. External sales remain source-reported only when publicly visible.
Country ranking = reserved architecture signal; India/CosmoFit preference is a future rule, not an MVP rule.
33. Current External Platform Notes
These notes are based on currently available public/official platform documentation and should be re-checked when the importer is implemented because external page structures and terms can change.
Gumroad product/profile pages expose catalogue-related public data in certain page contexts, and Gumroad supports custom product URLs.
Payhip provides direct product URLs and product pages with title, description, images and visibility options.
Lemon Squeezy product data includes name, description, thumbnail URLs, price and a buy-now URL in its product object, while its product setup supports multiple product images. The MVP importer will not use the API, but these documented fields help define the normalized data model.
The exact CosmoFit domain/page structure should be validated with a real product URL before its adapter is finalized. The name 'CosmoFit' is ambiguous on the public web, so the implementation should not hard-code an unverified domain.
